# Speed experiments (autonomous run)

Goal: bring the overall time down without going below Q4. Dropping layers
is allowed. Every idea is listed with what was tried and what happened,
kept or not. Starting point and context: [performance.md](performance.md).

## Method

- **Device:** Cardputer-Adv, SD at 80 MHz (1-bit), model `lfm-q4-head-lr256.lfm`
  (Q4 everywhere, low-rank LM head shortlist), int8 activations, PIE SIMD.
- **Harness:** `tools/bench.py` uploads the prompt and `/cfg.txt` knobs, then
  reads the firmware's `RESULT` line. All runs are logged in `out/bench_log.jsonl`.
- **Benchmarks:**
  - **B1:** "The capital of France is" (6 tokens) until end-of-text. The
    answer is " Paris." + `<|im_end|>`, so 3 generated tokens.
  - **B2:** "Here is a list of the eight planets of the solar system, in order
    from the Sun:" (20 tokens), then 12 generated tokens (EOS ignored). The
    answer is "\n\n1. Mercury\n2. Venus…".
- **Quality checks** for lossy ideas run on the Mac with `lfm_eval`
  (perplexity, top-1 agreement over 419 tokens of mixed text).

## Baseline (start of the run)

| | B1 total | B1 prompt | per token (B2) | B2 prompt |
|---|---|---|---|---|
| speculative, up to 5 drafts per pass | 41.27 s | 13.20 s | 14.06 s | 46.46 s |

## Where it ended

All lossless relative to the Q4 model except where noted (low-rank / flash LM
head: 99.5% next-token agreement with the full head on the host).

| | start of the run | end of the run | |
|---|---|---|---|
| B1 total ("The capital of France is" → " Paris.") | 41.27 s | **34.68 s** | −16% |
| B1 run again (prompt cache) | 41.27 s | **23.39 s** | −43% |
| B2 per generated token | 14.06 s | **7.48 s** | −47% |
| B2 prompt (20 tokens) | 46.46 s | **33.27 s** | −28% |
| B2 total (20 + 12 tokens) | ~215 s (14.06 s × 12 + 46.5) | **115.5 s** | −46% |
| *after #30 (draft head)*: B1 total | | **23.6 s** | −43% |
| *after #30*: B2 per token / total | | **5.61 s / 95.0 s** | −60% / −56% |
| *after #31–35 (flash 120 MHz, two-core scan, streamed SD)*: B1 / B2 per token / B2 total | | **21.0 s / 4.97 s / 84.6 s** | |
| *after #39–40 (tree drafts, lazy re-score)*: B2 per token / B2 total / chat per token | | **4.39 s / 78.2 s / 6.10 s** | |

Biggest wins: self-generated n-gram drafts (#5), LM head table in flash
(#11–18, #23), prompt batch 7 (#19), prompt cache (#27). Rejected: layer
dropping (#7) and MLP sparsity (#8) wreck the model; confidence-gated or
adaptive drafts (#6, #24) don't beat plain k=2.

## 29 in detail: Wi-Fi + SD in parallel

**Idea.** The card is busy 92–93% of every pass at ~9 MB/s, so a second,
independent source of weight bytes would cut the pass time. The ESP32-S3 has
Wi-Fi; the Mac can serve the model file. Split each 32 KB block: the card
reads part, a TCP stream brings the rest, both into the engine's own buffers.

**Setup (code removed afterwards; it is in git history at commit 5867142).**
- Mac: a ~60-line Python server answering requests of
  `<uint64 offset, uint32 length>` with that range of the `.lfm` file
  (`os.sendfile`), several requests in flight per connection.
- Device: a test mode (no model) that joined the network from
  `/sdcard/wifi.txt`, fetched 16 MB in 32 KB requests, CRC-checked the first
  1 MB against the same bytes from the card, then ran Wi-Fi and SD reads at the
  same time. Power save off (`esp_wifi_set_ps(WIFI_PS_NONE)`).
- 2.4 GHz home router, RSSI −49 to −70 dBm across runs.

**Measurements** (SD alone, same loop: 9.31 MB/s).

| Wi-Fi config | Wi-Fi alone | Wi-Fi + SD together | RAM taken by Wi-Fi |
|---|---|---|---|
| default lwIP, 16 static / 32 dynamic RX buffers, 32 KB TCP window | 2.9 MB/s (2 requests in flight; 1: 2.2–2.7, 4: no better) | 2.1 + 8.7 = **10.8 MB/s (+16%)** | 61 KB connected, ~121 KB at peak |
| 8 / 16 RX buffers, 16 KB window | 1.8 MB/s | 1.6 + 8.7 = 10.3 MB/s (+10%) | 48 KB connected, ~73 KB at peak |
| same, Wi-Fi IRAM optimisations off | 1.4 MB/s | 1.2 + 8.5 = 9.8 MB/s (+5%) | same, but +17 KB heap at boot |

**What the test runs showed.**
- *Where lwIP runs matters.* Unpinned, the lwIP task lands on core 1 next to
  the SD reader: Wi-Fi 2.8 + SD 6.9 = 9.7 MB/s, barely above the card alone.
  Pinned to core 0 (`CONFIG_LWIP_TCPIP_TASK_AFFINITY_CPU0`): SD keeps 8.7.
- *A first version of the test was wrong.* The SD loop ran in the main task
  (priority 1, core 0) and starved behind the Wi-Fi tasks: the card sat idle
  between reads (SD 5.4 MB/s, total 8.3, *less* than the card alone). The
  real reader runs at high priority on core 1; the test had to do the same.
- *Heap "minimum since boot" lies* when an earlier stage (the USB upload
  buffers) dipped lower; the peak has to be measured with
  `heap_caps_monitor_local_minimum_free_size_start()`.
- Wi-Fi throughput moves with the radio conditions; a split ratio would have
  to adapt per block, or a slow stretch stalls the whole matrix.

**Why it was not built into the engine.** RAM. With the engine loaded the
heap has ~35 KB free, and every step of prompt batch costs 25 KB. Even the
small Wi-Fi config (~73 KB at peak) forces the prompt batch from 7 down to
3–4. Estimates for B2 (20-token prompt, 12 tokens): generation ~9% faster
(7.5 → ~6.8 s/token), the prompt ~2× slower (33 → ~60 s), total
~115 → ~145 s. It only pays off past ~45 generated tokens per prompt, and it
makes the device depend on a Mac running a server. The bigger buffers that
gave +16% need RAM the device doesn't have.


## 30 in detail: draft head

**Why.** The n-gram table drafts from the last two tokens only. On ordinary
text and chat replies it is rarely right (B1: 0 of 4 drafts; a chat "Hello":
0 of 18), so most passes give one token.

**What.** After each pass the engine has h, the final (normed) hidden state
of the position that produced the newest token `fed`. One shared step,
applied once per draft:

    h' = h + up(silu(down([h, rmsnorm(embedding(fed))])))      down: 2048 -> 512, up: 512 -> 1024
    draft = argmax(LM head(final_norm(h')))                    then feed h' and the draft to the next step

Trained (`tools/draft_heads.py`) on the hidden states of the Q4 model over
3.2M positions of its own greedy text: WikiText openings, Alpaca prompts in
three shapes and 6000 ChatML chat turns (`tools/selfgen_corpus.py`). Only
positions where the text continues the way the Q4 model would are used.

**Simulated first** (20 chat prompts, 20 clean prompts, k = 2, tokens per pass):

| drafter | chat | clean |
|---|---|---|
| n-gram table (what was on the device) | 1.21 | 1.31 |
| Medusa heads (one per depth, no token input), WikiText-only training | 1.18 | 1.28 |
| recurrent head, WikiText-only training | — | 1.42 |
| recurrent head rank 256, mixed corpus | 1.56 | 1.62 |
| recurrent head rank 512, mixed corpus | 1.63 | 1.64 |
| prompt lookup, then recurrent rank 512 | **1.67** | **1.66** |
| same, head weights in Q4 (what ships) | 1.65 | 1.66 |

Training data mattered most: trained on WikiText only, the head was right
51% of the time on held-out WikiText but ~31% on the clean prompts. Feeding
the drafted token back in (recurrent) beats separate per-depth heads.

**On the device.** Rank 512, Q4: 0.86 MB in the flash partition that held
the n-gram table (`tools/draft_heads.py export`, `tools/flash_part.sh ngram
out/dhead.bin`). Per draft: embedding row (flash cache or SD), two matvecs
from flash, then the flash LM-head table scan with only the top 16 candidates
re-scored. Engine scratch slots hold the temporaries, so no extra RAM.
Measured: 1.71 tokens/pass on a 48-token chat reply (host prediction 1.70),
drafting ~0.22 s per draft, i.e. a pass costs ~12.4 s instead of ~11.7 s.
Output stays identical to greedy (host test
`Speculative.DraftHeadSameTokensAsGreedy`).

Not done yet: k = 3 on the device (simulation: 1.75 vs 1.67 tokens/pass, but
each draft costs ~0.22 s); a cheaper draft LM head (the full-vocab table scan
is most of the 0.22 s; restricting to the 16K most frequent ids would miss 14%
of tokens).

## Not tried (and why)

- **Below Q4 / pruning weights:** out of scope (the brief keeps Q4 as the floor).
- **Faster flash (120 MHz):** see 26.
- **A staging buffer so conv state / KV use doesn't cancel the prefetch:** ~14 stream starts per pass × 3.6 ms ≈ 0.05 s (0.4%).
- **Both cores computing:** SD is busy 92–93% of the time; compute already hides behind it.
- **Tree / multi-candidate speculative drafts:** needs tree attention; current single-chain acceptance (~1.3 tokens per pass) suggests little headroom with these drafters.
